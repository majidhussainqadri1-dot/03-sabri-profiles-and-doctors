## Additional adversarial source/CI review: D17 and D18 — 2026-11-14

### D17: MySQL implicit COMMIT on a recursive transaction

**Root cause:** New V12.3 D14 Future-profile methods (\`save_translation\`, \`reconfirm_field\`, \`set_future_state\`) correctly began owner-mutation transactions, but the REST \`SPD_Future_REST::mutate\` wrapper already held a separate \`SPD_DB::transaction\` for idempotency finalization. The original helper unconditionally ran \`START TRANSACTION\` on every invocation. In MySQL/MariaDB, a second \`START TRANSACTION\` implicitly commits the first transaction, so an outer idempotency-finalize failure could no longer roll back an already committed inner owner mutation/outbox.

**Proof and correction:**
- Actual helper + MySQL behavior fake-DB test: \`tests/nested-transaction-atomicity-runtime.php\`.
- Fail-first source commit \`d99282ab78134f0a09b25d9eda8054fb385cc3ab\`, Fresh Eighty workflow run \`43597730233\`: failed at the new nested transaction gate.
- Correction \`includes/class-spd-db.php\`: maintain request-local transaction nesting depth; only outermost scope executes \`START TRANSACTION/COMMIT\`; nested scopes use InnoDB \`SAVEPOINT/ROLLBACK TO SAVEPOINT/RELEASE SAVEPOINT\`. A failed rollback/savepoint marks outer transaction compromised so it cannot return an apparent success.
- Strengthened previous 80-round static assertion, rather than disabling it; \`tests/eighty-round-review.py\` now requires both normal transaction commands and nested savepoint proof.
